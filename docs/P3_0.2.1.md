# P3 - explicit environment controls and recovery (0.2.1)

Android version 0.2.1/code 13 exposes 40 MCP tools. The goal is truthful,
capability-aware setup, not privileged control that an ordinary phone app cannot
deliver. iOS tool surfaces are unchanged.

## Owned device-state recovery

`device_state` now requires a caller-generated random URL-safe `state_key`,
32-128 characters, for `set`, `status` and `restore`. Retain it **before setup**,
outside source control and reports. An approved session plus the key authorizes
recovery after reconnection/process restart; client names do not establish ownership.
Sharing the key intentionally delegates recovery access.

```json
{
  "name": "device_state",
  "arguments": {
    "action": "set",
    "state_key": "<caller-generated recovery secret>",
    "animations": false,
    "volume": 30
  }
}
```

Invoke `status` or `restore` with the same key. Another key cannot change or
restore the pending snapshot. Only one owner can hold pending device state.
Repeated sets by that owner preserve the first original for each touched field.

The whole request is validated/preflighted before mutation. Originals for only
the touched fields are durably journaled before any write, including originally
unset settings. The Android AtomicFile journal stores a hashed owner and bounded
numeric/boolean setting values, not the recovery secret. It is separate from the
P2 run database: there is no scenario/run environment syntax in this release.

Supported fields:

| Field | Requirement | Verification |
| --- | --- | --- |
| `rotation` | Explicit WRITE_SETTINGS access | Rotation policy/value and effective display rotation for fixed orientation |
| `font_scale` | Explicit WRITE_SETTINGS access; range 0.85-2.0 | Stored scale and effective Tester resource configuration |
| `animations` | Explicit WRITE_SECURE_SETTINGS provisioning | All three animation-scale settings |
| `volume` | Non-fixed media-volume policy; integer 0-100 | Actual media stream index after platform rounding |
| `keep_awake` | WAKE_LOCK declared by Tester | Owned wake-lock held state; bounded to 30 minutes |
| `dark_mode` | Unsupported | Setting-only `ui_night_mode` writes do not establish visible theme changes |

Successful sets return `verified_fields` and numeric/boolean `readback` values.
Readback is a measured state, not a guarantee against later user/OS changes.
The wake-lock flag does not prove that every OEM will keep a display lit.
Setup never grants its own privileges.

On a platform write/readback failure or request cancellation, the owner receives
bounded cancellation-safe restoration. A failed setup remains non-success even
when rollback succeeds. Explicit restoration has its own five-second cooperative
budget. Each successfully restored field is removed durably; failed/unattempted
fields remain pending for retry after fixing permissions/policy. Synchronous
framework calls are not hard-real-time interruptible.
Cancellation/response loss after a completed set can still leave owned pending
state; inspect with the original key rather than assuming rollback.

`get_device_state` and `get_capabilities` expose pending recovery without revealing
the owner key. Process restart never resumes a set or silently discards originals:
use the original key to inspect/restore. Server stop/disconnect does not imply
cleanup; a pending successful set remains explicit until restore or native QA end.
Keep the key: there is no unowned/force-restore bypass.

Native `qa_session begin` only reads device information; it no longer snapshots
every field. Native `qa_session end` accepts `state_key` to restore owned pending
fields; missing/wrong keys or partial cleanup make the report FAIL and leave
recovery pending. The gateway's unprefixed `qa_session` only manages its report.
Scenario setup/cleanup orchestration and run-linked recovery remain P4.

**Migration:** old `device_state set/restore` calls without a key must be updated.
Global dark-mode writes now fail rather than report success for a setting that may
not affect the UI. No automatic arbitrary shell/ADB fallback is introduced.

## Explicit app links

`open_link` requires `package_name`, `uri` and optional `wait_ms` (250-30000,
default 5000). It accepts bounded hierarchical HTTP(S)/custom app links without
embedded credentials. File/content/intent/data/script/telephony and other
system-action schemes are rejected.

Exactly one enabled, exported, permission-free browsable activity must resolve
inside the explicit target. Tester dispatches ACTION_VIEW to that component,
with only its internal NEW_TASK flag; arbitrary components/extras/flags are
rejected. Accessibility is required before dispatch for bounded target-foreground/
quiet verification. Android package visibility/background-start restrictions
still apply.

Readiness does not prove the target handled a specific business route: assert
the resulting UI. A launch timeout may follow a real side effect; never blindly
retry. URI arguments/results are omitted from native command history/gateway
reports, including gateway failure details.

## Write-first clipboard

The sensitive `clipboard` tool supports:

- `write` with plain `text` (max 5000 characters), replacing the current clipboard
  without reading/saving it; marks the new clip sensitive.
- `read_owned` only for an unchanged plain-text clip written by this approved
  session in this process.
- `clear_owned` with the same ownership/content checks, never restoring an
  unrelated previous clipboard.

Tester must be foreground. Session identity, a random clip marker and a content
digest gate read/clear; process restart loses that authorization. No URI/provider
coercion or background app switching is used. Clip content is omitted from command
history/gateway reports; an approved read returns it to the caller.

Android has no atomic compare-and-clear operation. A concurrent external clipboard
replacement can race validation/clear; this is not a transactional clipboard API.
Automatic cleanup must not claim it restored another app's previous clipboard.

## Environment inspection

`get_test_environment(package_name)` returns bounded manifest permission/grant
flags and the inspectable app-locale override. Permission flags do not prove
app-ops, one-time permission or device-policy access. App-locale queries can be
denied by READ_APP_SPECIFIC_LOCALES/installer restrictions. An empty override
does not prove the effective locale chosen by the target.

Permission/locale mutation, developer-provisioned mock location, destructive app
data reset, device-time mutation and arbitrary launch arguments remain explicitly
unsupported with actionable host/managed-device/target-hook requirements.
There is no configured privileged adapter and no arbitrary shell channel.
Connectivity changes remain deferred to avoid stranding remote runs.

## Manifest provenance contract v1

Targets may expose application metadata:

```xml
<meta-data android:name="com.vlad.tester.provenance.schema" android:value="1" />
<meta-data android:name="com.vlad.tester.provenance.sha" android:value="${sourceSha}" />
<meta-data android:name="com.vlad.tester.provenance.artifact" android:value="${artifactId}" />
```

The target build must supply these manifest placeholders; Tester does not
interpolate them at runtime. SHA is 40/64 hex characters; artifact is an opaque
1-160 character identifier using letters, digits, dot, underscore or hyphen,
not a credential-bearing URL. Schema 1 and at least one valid identity field
are required if any contract field is present.

`get_build_identity` labels valid claims `app_reported_unverified` and
`independently_verified:false`. Missing metadata remains `unknown`; malformed
metadata returns `invalid_contract` and `isError:true` without echoing arbitrary
claims. Install/update dates never establish that a fix is present.
The QA fixture contains deliberately synthetic, non-CI metadata for this contract.

## Privacy, execution and validation scope

New mutation tools use the native approval gate and device serialization, with a
separate ten-second queue budget. Recovery keys are excluded from approval text,
command history and gateway call reports. Native QA report contents remain
explicitly caller-authored data, not a generally redacted report channel.
Gateway session-loss handling never replays environment mutations.

Validation uses the separate synthetic target on an owned disposable API 35
emulator, not personal apps or a physical-device replacement. Coverage includes
ownership conflicts, touched-field restoration, font/wake-lock readback, app-link
delivery/rejected schemes, foreground/session clipboard isolation, provenance,
permission inspection, and native QA cleanup. Separate probes revoke secure-setting
access during restoration, force-stop Tester and recover the original pending
fields in a new approved session, preserving originally unset animation settings.

Host tests cover persist-before-dispatch, whole-request preflight, storage failure,
original preservation, partial restore retry, restart and cancellation-safe cleanup.
The release checks passed 87 Kotlin host tests, 17 gateway tests and 33 live
API 35 contracts (4 P0, 12 P1, 8 P2 and 9 P3), plus the separate permission-loss/
process-restart probes. The cleanup-failure probe also inspected the persisted QA
JSON and confirmed result FAIL with no recovery key in the report.
Android/fixture debug builds and lint passed.
This is not an OEM-wide/platform-wide certification. Privileged adapters are
intentionally not claimed as implemented.
