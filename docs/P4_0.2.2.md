# P4 - saved scenarios, cleanup and native CI (0.2.2)

Android version 0.2.2/code 14 exposes 43 MCP tools. iOS surfaces are unchanged.
The existing native evaluator, device lock, consent and durable run store remain
the only execution engine. YAML is an optional frontend, not the product boundary.

## One versioned scenario model

`run_route` accepts exactly one input source:

- `yaml`: bounded inline Tester YAML, schema 1 or 2.
- `scenario`: the equivalent structured JSON object.
- `route_id`, `version`, `digest`: an exact immutable APK-bundled catalog definition.

All sources share the same compiler, typed parameter binding and native actions.
Schema 1 remains compatible. Schema 2 requires `version: major.minor.patch` and
supports these ordered phases: `setup`, `preconditions`, required `steps`,
`postconditions`, then `cleanup`. UI preconditions check the prepared target app
before business actions, not the dashboard foregrounded for manual consent.
Environment validation/permission preflight still precede all setup side effects.
Preconditions/postconditions accept only `wait`/`assert`; bounded waits retry observations, never actions. No loops,
scripts, conditional branching or subscenario calls are supported in this release.

```yaml
schema_version: 2
id: project.open
version: 1.0.0
platform: android
app_id: com.example.projects
timeout_ms: 15000
cleanup_timeout_ms: 10000
parameters:
  name: {type: string, default: "Project Beta"}
setup:
  - device_state: {keep_awake: true}
  - launch_app: {}
  - wait: {condition: idle, timeout_ms: 3000}
steps:
  - tap: {resource_id: open, within: {content_desc: "${name}"}}
postconditions:
  - assert: {condition: text, resource_id: title, expected: "${name}"}
cleanup:
  - back: {}
```

In addition to schema 1 commands, setup permits `device_state` fields
`rotation`, `font_scale`, `animations`, `volume`, `keep_awake` and `open_link`
with `uri`/optional `wait_ms`. Target package comes from `app_id`; arbitrary
flags/components/extras or different packages cannot be injected into steps.
State setup preflights every requested field before admission/side effects;
it never grants permissions. Platform policy can still change after preflight.
App-link readiness does not establish a business postcondition.

Limits remain 32768 definition characters, 12 nesting levels, 20 typed parameters
and 50 total expanded steps across all phases, including automatic restoration.
The main deadline is 1–60000 ms and starts after approval/device-lock acquisition.
No approvals, captures or implicit idle waits occur inside tap/delay/Back.

## Cleanup and ownership

The runner stops main execution on its first failure and never retries actions.
It attempts declared cleanup after setup/check/test failure, deadline or
cancellation. Cleanup steps are independently attempted even if an earlier cleanup
action fails. Cleanup has its own 1000–15000 ms cooperative deadline (default
10000); state-changing scenarios require at least 6000 ms and reserve 5000 of that
budget for automatic P3 restoration after user cleanup. Cleanup cannot erase the
primary failure; `primary_status` and `cleanup_status` are separate.

Every setup `device_state` uses the caller's `run_key` as the P3 `state_key`.
Generate and persist that key before submission. Only touched originals are
persisted before writes, and the runner appends `cleanup_state` automatically.
Restore is attempted even when user cleanup fails or times out. Successfully
restored fields are removed; failures remain owned and durable. After restart,
unfinished runs are `interrupted`, never resumed; inspect `get_run`, then use
`device_state status/restore` with `state_key` equal to the original `run_key`.
Keep the key; there is no force-restore bypass.

`pending_cleanup` concerns declared cleanup, not transactional rollback of app
business data. `pending_state_restore` separately identifies journal recovery.
A failed cleanup makes an otherwise passing run fail. Synchronous Android calls
remain cooperatively timed, not hard-interruptible. Process death cannot run
arbitrary UI cleanup; pending originals survive for explicit recovery.

## Reviewed discovery and bounded CI consent

`list_routes` advertises three definitions, stored in
[`androidApp/src/main/assets/tester-routes`](../androidApp/src/main/assets/tester-routes):

| Route | Version | Postconditions |
| --- | --- | --- |
| `fixture.named_project` | 1.0.0 | Beta opened, exactly one action; unique container-scoped Open |
| `fixture.unicode_form` | 1.0.0 | Unicode value in Beta, Alpha unchanged, zero unintended actions |
| `fixture.tap_delay_back` | 1.0.0 | Returns from Compose to cards with zero Open actions |

These are synthetic fixture scenarios, not reviewed routes for arbitrary apps.
`get_route(route_id, version)` returns YAML and SHA-256 of exact source bytes.
Execution requires that exact digest too; no `latest` alias or client catalog edits.
Changing a definition requires a repository/APK release and reviewed version bump.
The separate fixture resets its synthetic cards on each explicitly delivered link.
`open_link` now uses internal NEW_TASK + SINGLE_TOP so Android delivers a repeated
link to `onNewIntent` rather than merely foregrounding an identical existing task.
Clients still cannot supply flags; target apps must handle their own link semantics.

For unattended CI, call `route_policy` with `action: grant`, exact catalog identity,
optional typed `parameters`/`privacy_sensitive`, `max_runs: 1..30` and
`ttl_ms: 1000..900000` (defaults 1 and 600000). **Grant always requires explicit
dashboard approval**, even if the global sensitive-tool confirmation switch is off.
The dashboard shows every expanded phase/action, privacy, attempt count and expiry.
The returned `policy_id` can be used only by the same approved session in that
server process, for that exact expanded catalog plan and privacy policy.
Parameter/definition/privacy changes fail closed, without falling back to approval.
At most 32 policies are retained; `status`/`revoke` need the owning session.
Server stop clears policies. Session loss/restart requires fresh approval.

Each fresh admitted attempt consumes one slot; deduplicated submissions do not.
Failed/rejected attempts are not silently retried or replaced. Status/cancellation
and recovery still require the run's retained key, not the policy ID.
No global confirmation bypass or arbitrary shell/ADB execution is added.

## Canonical reports and CI CLI

`get_run` is the authoritative redacted run with phase/step IDs, status, offsets,
durations, delay requests and cleanup outcome. `export_run` supports `json`,
`markdown` timeline and `junit`. It returns an opaque stored artifact ID plus
identical bounded redacted `content` inline; this avoids requiring approval to
download an already-authorized redacted text report. Unmasked image reads still
require their existing consent/ownership. Reports omit keys, parameters and UI text.
JUnit includes the native step IDs and a run verdict; active, interrupted, cancelled,
failed or cleanup-pending runs cannot produce a passing CI verdict.

The gateway forwards these APIs without parsing/executing scenarios. Its call
history records only a native run-ID reference, not a competing copy of the timeline.
It does not replay submissions/policy changes after session loss.

The standard-library CLI connects directly to native HTTP MCP:

```bash
# Provision device, install Tester + fixture, enable accessibility and approve
# this MCP session first. Keep sensitive confirmations ON.
# TESTER_MCP_SESSION / optional TESTER_MCP_TOKEN are private environment values.
# Obtain exact version/digest through list_routes/get_route and approve a matching
# route_policy grant in the dashboard before passing --policy-id.
python3 tools/tester_ci.py \
  --url http://127.0.0.1:8080/mcp \
  --route fixture.named_project --version 1.0.0 --digest "$ROUTE_DIGEST" \
  --policy-id "$APPROVED_POLICY_ID" \
  --state /tmp/tester-attempt-001.json --output /tmp/tester-report-001

# Recover an accepted original, never launch a new attempt:
python3 tools/tester_ci.py --resume \
  --state /tmp/tester-attempt-001.json --output /tmp/tester-report-001
```

`--yaml file.yaml` and `--scenario file.json` use the same native engine;
`--parameters` accepts a JSON object. A new session can be initialized with an
optional token; without one, normal manual session approval applies. Session-owned
catalog policies must be granted in the same session supplied to the CLI.
HTTPS uses ordinary certificate verification; no insecure TLS bypass. Plain HTTP
is loopback-only (e.g. explicitly provisioned ADB forwarding), and redirects fail.

Before any submission the CLI saves its random recovery key/submission ID and
request digest in an owner-only file, then saves the run ID on acceptance.
The state file contains a bearer capability: never commit/upload it. Use a new
state path for each fresh attempt; rerunning the same submission can only recover/
deduplicate it. If the initial response was lost before recording a run ID,
explicitly resupply the same source/parameters to safely deduplicate; `--resume`
alone cannot guess them. Mutating requests are never automatically retried.

The CLI polls and writes `run.json`, `timeline.md`, `junit.xml` with owner-only
permissions. Exit 0 means native completion and successful declared cleanup;
1 means a terminal non-success; 2 means client/transport/export failure or a
polling deadline. A polling deadline does not cancel a possibly active run.
Use `--resume` or `--cancel` with retained ownership; cleanup/uncertainty remain
native responsibilities, not host-side replay. Export files are redacted; the
state file is not. Parent directory for the state file must already exist.

The bounded native store now retains at most 128 runs/8 active, 512 artifacts
and 20 MiB total artifact data (2 MiB per artifact), enough for the 90-run fixture
gate plus three CI report formats. Terminal retention remains 7 days, pruned on
admission; no long-term exactly-once claim is made.

## Verification scope and limitations

Release checks passed: 102 Kotlin host tests, 19 gateway tests, 8 CI-client
tests, Android/fixture debug builds and lint. All 33 P0-P3 native regression
cases passed on the disposable API 35 emulator. The P4 catalog gate passed
30 consecutive attempts for each of the three scenarios (90 total), with
postconditions, cleanup and stable native IDs checked under explicitly approved
policies while sensitive confirmations remained enabled.

The 30-attempt native duration median/p95 values were 1556/2423 ms for named
project, 1502/2048 ms for Unicode form and 3207.5/3577 ms for tap-delay-Back.
The requested 300 ms delay exceeded its request by 5-49 ms in that timing sample;
these are measured emulator timings, not hard-real-time guarantees.

Separate actual-device-service probes passed setup/test/cleanup failure,
cancellation, scope rejection, deduplication, CLI submit/resume/nonzero exit,
and partial restoration after permission loss and process restart. A new approved
session with the original key restored exact retained originals; a wrong key
was denied.

A five-sample loopback HTTP lower-bound comparison measured native versus
host-driven full-run medians of 3280.8 versus 3105.0 ms (nearest-rank p95:
4212.8 versus 3503.8 ms). Native execution reduced control calls from nine
to one and timing-window network round trips from two to zero, but was not
faster in this small sample. This comparison included no model thinking/network
latency and is not evidence of an LLM speedup. Only this explicitly provisioned
standalone comparison and legacy regression suite temporarily disabled sensitive
confirmations on the disposable emulator; confirmation was restored afterward.
The 90-run P4 unattended gate did not require that bypass.

Host contracts cover JSON/YAML parity, full validation, catalog pinning,
setup/check failure, independent cleanup deadlines, cancellation, storage failure,
restore failure, scoped-policy ownership/expiry/attempts and JUnit verdicts.
CLI contracts cover persist-before-submit, response loss, same-identity recovery,
nonzero failure/cleanup exits, bounded polling and private state.

The opt-in [`test_android_scenarios_mcp.py`](../tools/test_android_scenarios_mcp.py)
requires externally approved exact-plan policies; it never installs, changes
confirmation settings or grants its own authority. It checks 30 consecutive runs
per scenario, postconditions, cleanup, stable IDs and redacted exports.
API 35 synthetic results do not certify every OEM or arbitrary business app.
LLM planning latency is not equivalent to host HTTP latency; timing data must
identify which one was measured. P5 recording/Viewer/advanced adapters remain
unimplemented.
